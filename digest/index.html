博世用豆包工作：让工程师少搬信息，多解问题

头图来源：豆包工作 客户在群里抛出一个问题，到工程师真正坐下来分析故障，中间隔着多少工作？ 在博世的某研发事业部，答案曾经是：找齐散落在各个群和私聊里的消息，按多个维度整理成完整描述，凭经验判断该找谁，接着再开会，再把结论写成报告。 故障分析还没开始，大半天已经过去了。 如今，这中间的一大段路，工程师交给了豆包工作和豆包工作伙伴。 博世的尝试：让 AI 接手沟通之后的工作 汽车产业链企业的研发部门，经常会遇到这样的情况：一个工程师要当三个用：研发细节要盯，还有很多日常重复的活儿需要做。 博世某事业部的工程师，其所在的团队需要对接各家客户，为客户提供系统综合解决方案。面对同一家客户，不同项目会有不同的群，测试、路试、投产任何一个环节出了问题，消息一条条蹦出来：哪个项目、哪个软件、报了什么故障代码、出现什么报错。 他得把这些碎片按不同的数个维度整合起来，所属项目、软件版本、车辆配置、测试工况、报错时间、诊断截图都在其中，再凭经验自己排障，或者转给负责对应模块的研发同学。解释不清的就拉会，双方澄清之后，再出报告发给客户。 让这位工程师下决心改变的，是两件事。 一是知识沉淀靠不住。经验都装在工程师个人脑子里，云文档、知识库不是没有，但每个人的模板和习惯不同，项目一忙，没人顾得上往里放。新问题来了还得先找人，人一走，经验就断档，这个恶性循环一直破不掉。 如果沉淀这件事不再靠自觉，不管是消息还是会议，AI 能在人无感的状态下自动记下来，那就可以节省很多时间精力。 二是客户不会按模板提问。问题是流式发生的，消息不停往外蹦，没人能把故障代码、截图和十四五条字段在一条消息里一次性给齐。碎片攒不齐，后面的分析就迟迟开不了工。 豆包工作和豆包工作伙伴的加入解决了这些问题。 在工程师真实的日常工作中，问题通常是从私聊开始的，工程师可以在豆包工作里配置定时任务，巡检自己收到的私聊消息，识别出故障类信息，再以本人身份转发到问题报告专项话题群。 在这个流程里，客户的沟通习惯不用改，工程师少了手动搬运，散落在流程外的事被拉回了流程里。 消息进了专项群，每个问题占一个独立话题，不同任务的材料互不混杂，天然形成「一事一议」的界面。 豆包工作伙伴爬取群里的历史上下文，把流式蹦出来的碎片聚成完整的问题描述，再调用封装好的报告生成技能，按标准模板出初稿，同时登记进飞书多维表格，提醒对应工程师处理。 在一次真实的问题处理记录里，AI 把消息整理成飞书文档，问题状态标为「进行中」；驱动形式、驾驶模式这些没给全的信息，就保留「待补充」，工程师需要做的就是在初稿上核对、补齐，不必从空白文档开始。 还有些细节只有在开会时才能敲定下来。 工程师可以邀请豆包工作伙伴参加问题沟通会，它全程旁听，散会后直接把会上澄清的信息同步进报告，讨论、记录和报告之间，省掉了人工转述的环节。按工程师自己的估算，AI 初稿能覆盖七八成内容，剩下两成交给人判断；会议结论补完，报告基本齐活，再经人工复核一遍，才发给客户。 报告同时会归档进团队知识库，状态和进度留在多维表格：表格管跟进，知识库管留存。再遇到相似问题，AI 检索历史材料，先给出初版台账和归因。 它能调用的知识分两类：一类是外部行业知识，比如通用故障码各自代表什么含义；另一类是团队自己的历史沉淀，哪怕是已经离职的老工程师当年处理过的问题，也能被翻出来引用。 这个项目从需求到落地，用了短短一周多时间。事实上，豆包工作伙伴真正上岗的只花了一天，它进群跟工程师工作一天后，项目已经运转了起来，后面一周则用来调优细节，比如哪些报告写得太啰嗦，哪些内容不该放进去，哪些描述不够准确，工程师可以一条条告诉它：下次记住别再这么处理。培养一位 AI 数字员工，和带教一位新同事一样简单。 目前豆包工作伙伴前后跑了五六十份问题报告，已经能够稳定在七八十分的水平。 剩下的二十分留给人来最终把关。故障原因怎么定、验证计划怎么排、对外给什么结论，这些关键工作仍然要由工程师人工审核、补充和确认。 不起眼的工作里，藏着 AI 的真实价值 引入豆包工作后，工程师可以少搬一遍消息，少重写一份报告，遇到新问题可以从历史工作里查找处理经验，重复的步骤交给 AI，精力可以回到问题分析、验证和客户沟通这些更重要的事情上。 在一个人当三个用的团队里，这些是实打实的产能提高。 对团队来说，更深的变化在信息的流动。过去一次沟通结束，信息散在聊天记录、个人云盘和某个人的脑子里；现在消息自动变成任务、报告和知识库条目，一次次处理留下的记录，从个人文件变成同事可以共同使用的资产。 过去讨论 AI，注意力很容易放在它能不能替人完成复杂的专业任务——能不能写代码、做诊断、出方案。但在真实的知识工作里，专业判断只占时间的一部分，更多时间消耗在沟通之后：整理零散信息、记录会议结论、把问题转给对的人、跟进处理进度、归档留痕。这些事没有技术光环，琐碎、重复，却实实在在地占用人的精力。 就像在博世与豆包工作的合作里，AI 创造价值的位置，并非是工作流里最核心的那一环——把沟通、判断和解决专业问题留给人，把沟通之后的整理、记录和行动尽可能交给 AI，如此一来，工程师就能腾得出手，去做真正需要工程师来做的事。 AI 不一定要做最重要的事，才能创造重要的价值。

头图来源：腾讯云 过去一年，智能体是 AI 行业最受关注的方向之一。 从查资料、写文档到处理日常办公事务，桌面办公智能体完成了第一轮普及，办公提效的价值已经成为行业共识。但当 AI 进一步走向企业核心业务，搭出一个智能体不难，难的是让它真正跑进业务流程，适配复杂的系统、权限与规则，持续产出可量化的经营价值。 在腾讯云副总裁吴永坚看来，未来企业级智能体的核心赛道，对话式的桌面办公 Agent 已经完成了普及教育，员工用它处理文档、检索信息、辅助日常工作，个人效率的提升是普遍可感知的。 但在个人价值与企业价值之间仍然存在着一道鸿沟，麦肯锡 2026 年 8 月的全球 AI 调查给出了一组很有说服力的反差数据：80% 的人感受到了 AI 带来的个人效率提升，但只有不到四成的人认为 AI 真正为公司利润创造了正向贡献。 这个反差本身就是行业焦虑的来源—— 当所有人都在说 AI 提效，企业管理者真正关心的问题却没有标准答案。 顺着这个焦虑往下看，企业现在问的问题早就变了。大家不再问「智能体能做什么」，而是问「个人提效怎么变成业务增长」、「安全怎么管」以及「效果怎么评」。整个行业其实还没有一套固定的落地范式，从业务流程到组织架构，每家企业都在自己摸路。 腾讯集团副总裁、腾讯云 CTO 王慧星｜图片来源：腾讯云 腾讯集团副总裁、腾讯云 CTO 王慧星在和媒体交流时提到一个变化：过去是云厂商追着企业说数字化是必答题，现在反过来了，企业 CEO 主动找上门问这道题该怎么答。在他看来，平台方的角色也跟着变了，过去是把一个封闭的产品塞给客户，现在得把能力拆成原子化单元，和企业一起在真实业务里趟出路径。 事实上，Service Agent 和大家熟悉的办公助手，本质上是两个赛道。 吴永坚在接受采访时讲得很清楚，ADP 做的不是通用的 Agent 开发平台，而是专门面向数据和业务场景的 Service Agent 构建平台。这类智能体有两个绕不开的硬骨头——一是跨系统打通，要从合同、发票、业务记录这些分散在不同系统里的数据里统一口径，再做分析；二是权限体系严格对齐企业原有的身份机制，同一个问题，不同职级的人拿到的答案本来就该不一样。 行业的关注点已经发生了转移。搭出智能体 Demo，早已经不是什么难的环节。 真正难的是跨过四道实实在在的坎：AI 怎么安全接进公司内部系统，谁能看哪些数据；非专业人员怎么把知识和工具组织起来；跑起来之后怎么持续监测效果、成本和故障；公司建了一堆 Agent，员工却不知道有哪些、该用哪一个。 这也正好呼应了腾讯公司高级执行副总裁、腾讯云与智慧产业事业群总裁汤道生在主论坛上的判断——Agent 的使命要从内部协同走向业务经营，遵循业务规则、全天候运行，最终对实际的经营结果负责。 二、从搭建工具到业务载体，ADP 重做 Service Agent 的落地体系 那么问题就来了：要让 Service Agent 真正跑进业务流，平台到底要补哪些能力？这便是 ADP 这次全生命周期升级在回答的问题。 腾讯云副总裁吴永坚｜图片来源：腾讯云 现在行业里聊 Agent，大多还绕在个人助手、代码助手这类场景上，本质还是人提一个需求，AI 完成一个任务。但吴永坚判断，企业里更核心的 Agent 形态，早就跳出了这个框架——Service Agent 会嵌在真实业务流程里，由业务事件驱动，7×24 小时跑着，最终要对着可量化的经营指标交差。 可以想象几个非常日常的业务场景：债券交易群里弹出来一句「帮我拆一下这笔单」，智能体自动录系统、查持仓、走询价流程，关键节点再把人叫回来确认；几千家零售门店的监控摄像头每天涌进来几十万张画面，智能体自动识别陈列合规、货品缺货；上千名导购每天对着不同的客户，智能体实时生成贴合商品和用户的沟通话术。这些场景过去靠人工和规则系统撑着，未来就是 Service Agent 的主场。 而 ADP 这一轮全生命周期升级，其实就是在顺着「开放连接、原子化能力」的产品思路，对着前面那四道坎，一个一个补缺口。 构建层的变化最直观。过去企业想搭一个真能跑业务的 Agent，光有一个会聊天的对话框根本不够，后面要补前端操作页面、接后端业务逻辑、管数据状态，这些碎活往往占了项目八成的工作量。 这次 ADP 把智能体能力和站点服务打通了：智能体负责分析与执行，站点承载操作页面、业务逻辑和数据状态，企业可以直接搭建端到端的完整业务应用。加上自然语言构建能力的升级，从生成、调试、评测到发布全流程在一个工作区完成，懂业务的人描述需求就能搭出来，边聊边改。 ADP 的能力边界，也从「搭一个 Agent」延伸到了「搭一套能跑起来的业务系统」。 接入与治理这块，是企业级场景绕不开的硬门槛。 ADP 做的是私网直连，AI 通过企业内网连接数据库和业务系统，数据不用暴露在公网上；网络连接与租户、身份、数据权限深度绑定，明确「谁可以通过哪个 Agent 访问什么资源」。 每一次运行全链路留痕，成本和状态一目了然，出问题能定位到环节，版本可回滚；AI 从业务反馈里发现问题、给出改进建议，经人工审核后生效，机器持续学习，人始终把关。整个体系还开放了 100 多个接口和官方命令行工具，从产品界面调用到接口调用，安全、权限、审计的标准完全一致。 使用入口层面，等智能体真的建起来，新的问题就出现了：企业里攒了几十上百个 Agent，员工根本不知道有哪些、该用哪个。AgentPortal 做的就是这件事：作为企业智能体的统一入口，可按部门、岗位精准分发智能体，员工提问不用挑 Agent，系统自动派给最合适的智能体回答，没有对口的就由通用智能体兜底。再加上和 WorkBuddy 的双向打通，企业在 ADP 上构建的能力，可以分发到员工日常工作入口；员工验证过的有效流程，也能沉淀为企业可复用的智能体，企业能力服务个人，个人经验反哺企业，形成持续积累的循环。 同时，ADP 没有只做通用平台，还自己先做了两个垂类「样板间」。客服智能体覆盖从接待、业务办理到服务质检的完整流程，已经落地 200 多家标杆客户，平均解决率超过 85%；视觉智能体支持业务专家只要讲清「对与错」，Agent 就能自动理解要求、拆解任务，把模型和工具编排成完整工作流并持续运行，已经在一家零食品牌约 4000 家门店、13 万路摄像头落地，日均处理约 78 万张图片。 ADP 的角色已经变了——成为了支撑 Service Agent 全生命周期跑在业务里的载体。企业级 Agent 的竞争，也已经变成是谁的工程体系更扎实，谁能让智能体在复杂的企业环境里稳定、合规、持续地跑下去。 三、Agent 规模化落地，拼的是体系化能力 如果回头看大模型时代早期，行业关注的是模型参数与对话能力；Agent 刚兴起的时候，大家比拼的是谁搭得快、谁的场景多。走到今天，竞争的维度变了—— 拼的是谁能真的把 AI 嵌进企业的业务流程，让一个试点项目变成可复制的组织能力。
